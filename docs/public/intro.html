Sirius

Sirius is a small, imperative, total, polynomially bounded language for array programming.

Having been stung too many times massaging PyTorch tensors, I set off to design a type system that handles tensor shape bookkeeping. In the process, I explored a new part of PL design space and stumbled on an interesting set of features.

It turns out we can avoid runtime shape errors -- without the ergonomic strain of full-blown refinement types like Liquid Haskell -- provided we surrender shape dynamism. In exchange, we reject more bad programs and expose more complete function contracts. The Sirius type system will also unlock a bit of witchcraft in the backend.

I embedded a prototype compiler frontend in this page (sorry, Z3 Wasm builds don't seem to play nice on mobile). Here's a hello world: dot product and matrix multiplication.

// typevars, representing integers, come in curly brackets after function name
// "len(a) == len(b)" is proven at callsites
fn dot{N}(a: f32[N], b: f32[N]) -> f32:
    let mut sum = 0.0
    for i from 0 to N:
        // i is proven valid index into a and b
        sum += a[i] * b[i]
    return sum

// invalid shape calls fail to compile
fn matmul{I, J, K}(a: f32[I, J], b: f32[J, K]) -> f32[I, K]:
    for i from 0 to I:
        for k from 0 to K:
            // i is proven valid index into a
            // k valid into b' (b transpose)
            // dot_product requires a[i] and b'[k] have same length
            // total yield count is proven I*K
            // yield populates the return array in column-major order
            yield dot(a[i], b'[k])

That program doesn't seem very interesting until you try to change it. The compiler rejects accessing a[i+1] in dot, adding an extra yield in matmul, or modifying any of the typevar constraints in the function signatures. Here are some more examples:

// polynomial expressions in typevars are valid types
// "len(return) == A + B" is proven in function body
fn concat{A, B}(a: f32[A], b: f32[B]) -> f32[A + B]:
    yield from a
    yield from b

// N + 1 for typevar N is also valid type
fn push{N}(arr: f32[N], item: f32) -> f32[N + 1]:
    yield from arr
    yield item

fn fill{N}(val: f32) -> f32[N]:
    for i from 0 to N:
        yield val

fn test():
    let x = [1.0, 2.0, 3.0]
    // dot expects equal-len args
    // so fill(2) is inferred to be fill{3}(2.0) i.e. [2.0, 2.0, 2.0]
    let y = dot(x, fill(2)) // == 12.0

    // ! can't satisfy dot's call site constraints
    let z = dot(x, fill{4}(2))

Signatures provide shape bounds, accesses are statically checked, and yields are statically counted. In short, we're using refinement types with intentionally limited power and a built-in polynomial abstraction (Poly). Since the type system is constrained, the annotation burden stays low.[1]

# Design Rationale

Why make an imperative array language? In my opinion, the humble C-style for loop has gotten a bad rap. Sirius static analysis keeps most of its power and ameliorates the downsides. Some problems are easier to solve in an imperative, looping style, with mutable state and high locality.

That said, I plan to build functional and array-oriented facilities over the imperative core, like map and filter, fancy indexing, and a checked einops primitive integrated like regexes in Perl.

What do polynomials have to do with arrays? For one thing, multidimensional array access desugars to a polynomial.

ArrayAccessDesugar
A[N] A[i] deref(A + i)
A[N, M] A[i, j] deref(A + i*M + j)
A[N, M, P] A[i, j, k] deref(A + i*M*P + j*P + k)
A[N, M, M] A[i, j, k] deref(A + i*M^2 + j*M + k)

The desugared expression is a strategy for accessing an element given array coordinates, and it is polynomial in array dimensions. This is a polynomial ring. Add two Polys together, multiply them, or substitute a variable for a new one, and you'll always get a Poly back.

ArrayAccessDesugar
A[N, M + 1] A[i, j] deref(A + i*M + i + j)
A[N, 2*M] A[i, j] deref(A + 2*i*M + j)
A[N, M] A[3*i + 2, j + 5] deref(A + 3*i*M + 2*M + j + 5)

The Sirius type system permits the programmer to freely express array dimensions and accesses in terms of Polys -- as long as the resulting constraints can be solved by the Z3 prover.[2] The backend represents array access, strides, and offsets the same way.

Now, you might object: why can't the programmer write a function that yields an array of super-polynomial size? This is simple in most languages using a while loop or recursion; both are inexpressible in Sirius. Only for-iteration between Poly bounds is permitted.

Memory, compute, and optimization are all therefore subject to the same organs of static analysis. At this point, I hope I've convinced you that the Poly abstraction earns its keep.

There are various means to navigate the shape-data boundary in Sirius. typevars are available at runtime. Some operators can lift a normal value into a typevar by proving its bounds. Iterators behave like typevars. typevars compose algebraically, but any division that doesn't immediately simplify will demote the type expression to a plain integer. For example, (N^2-M^2)/(N+M) is the type N-M, but N/M is not a type, even given N=M.

Control flow is dictated by for-loops and if-statements. With flow typing, facts in if conditions are available to the constraint solver inside their scopes. Every yield must be counted symbolically.[3]. 

// a challenge for the yield counter
// typevar polys may only be written as sum-of-products in integer coefficients
// however, counting engine knows that inner for-body is invoked N(N-1)/2 times
fn triangle{N}() -> f32[N^2 - N + 1]:
    for i from 0 to N:
        for j from 0 to i:
            yield 0.0
            yield 1.0
    yield 2.0

Constraints that appear in function arguments must be proven at call sites and are available in the function body; vice-versa for constraints in the return type. Sirius also supports existential types, which are newly minted by function calls and can be constrained by st (such that) clauses. These clauses are proven in the function body and available at call sites.

// read as "N, K such that K is in 0<=K<N"
// this constraint is proven in function body
fn find{N, K st K \in N}(needle: f32, haystack: f32[N]) -> K?:
    for i from 0 to N:
        if needle == haystack[i]:
            // 'K \in N' constraint is proven here
            return i
    // K? is nullable K
    return null

fn test():
    let arr = [1.0, 2.0, 3.0]
    let k = find(2.0, arr)
    if k != null:
        // find() constraint is available at call sites
        // so this access is proven safe
        arr[k] += 1.0
