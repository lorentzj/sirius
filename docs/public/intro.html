Sirius

Sirius is a small, imperative, total, polynomially bounded language for array programming.

Having been stung too many times massaging PyTorch tensors, I set off to design a type system that handles tensor shape bookkeeping.

It turns out we can make one -- without the ergonomic strain of full-blown refinement types like Liquid Haskell -- provided we surrender shape dynamism. In exchange, we reject more bad programs and expose more complete function contracts. The Sirius type system will also unlock a bit of witchcraft in the backend.

I've embedded a prototype compiler frontend in this page. Here's a hello world: dot product and matrix multiplication.

// typevars, representing integers, come in curly brackets after function name
// "len(a) == len(b)" is proven at callsites
fn dot{N}(a: f32[N], b: f32[N]) -> f32:
    let mut sum = 0.0
    for i from 0 to N:
        // i is proven valid index into a and b
        sum += a[i] * b[i]
    return sum

// invalid shape calls fail to compile
fn matmul{I, J, K}(a: f32[I, J], b: f32[J, K]) -> f32[I, K]:
    for i from 0 to I:
        for k from 0 to K:
            // i is proven valid index into a
            // k valid into b' (b transpose)
            // dot_product requires a[i] and b'[k] have same length
            // total yield count is proven I*K
            // yield populates the return array in column-major order
            yield dot(a[i], b'[k])

This program doesn't seem very interesting until you try to change it. The compiler rejects accessing a[i+1] in dot, adding an extra yield in matmul, or modifying any of the typevar constraints in the function signatures.

// polynomial expressions in typevars are valid types
// "len(return) == A + B" is proven in function body
fn concat{A, B}(a: f32[A], b: f32[B]) -> f32[A + B]:
    yield from a
    yield from b

// N + 1 for typevar N is also valid type
fn push{N}(arr: f32[N], item: f32) -> f32[N + 1]:
    yield from arr
    yield item

fn fill{N}(val: f32) -> f32[N]:
    for i from 0 to N:
        yield val

fn test():
    let x = [1.0, 2.0, 3.0]
    // dot expects equal-len args
    // so fill(2) is inferred to be fill{3}(2.0) i.e. [2.0, 2.0, 2.0]
    let y = dot(x, fill(2)) // == 12.0

    // ! can't satisfy dot's call site constraints
    let z = dot(x, fill{4}(2))

Signatures provide shape bounds, accesses are statically checked, and yields are statically counted. In short, we're using refinement types with an intentionally limited scope. Since the type system is constrained, the annotation burden stays low.[1]

# Design Rationale

Why make an imperative array language? In my opinion, the humble C-style for loop has gotten a bad rap. Sirius static analysis keeps most of its power and ameliorates the downsides. Subjectively, some problems feel easier to solve in an imperative, looping style. Sirius is just exploring a new part of design space.

That said, I plan to build functional and array-oriented facilities over the imperative core, like map and filter, fancy indexing, and a checked einops primitive integrated like regexes in Perl.

What do polynomials have to do with arrays? For one thing, multidimensional array access desugars to a polynomial.

ArrayAccessDesugar
A[N] A[i] deref(A + i)
A[N, M] A[i, j] deref(A + i*M + j)
A[N, M, P] A[i, j, k] deref(A + i*M*P + j*P + k)
A[N, M, M] A[i, j, k] deref(A + i*M^2 + j*M + k)

The desugared expression is a strategy for accessing an element given array coordinates, and it is polynomial in array dimensions. This is a polynomial ring. Add two Polys together, multiply them, or substitute a variable for a new one, and you'll always get a Poly back.

ArrayAccessDesugar
A[N, M + 1] A[i, j] deref(A + i*M + i + j)
A[N, 2*M] A[i, j] deref(A + 2*i*M + j)
A[N, M] A[3*i + 2, j + 5] deref(A + 3*i*M + 2*M + j + 5)

The Sirius type system permits the programmer to freely express array dimensions and accesses in terms of Polys -- as long as the resulting constraints can be solved by the Z3 prover.[2] The backend represents array access, strides, and offsets using this abstraction.

Now, you might object: why can't the programmer write a function that yields an array of super-polynomial size? This is simple in most languages using a while loop or recursion; both are inexpressible in Sirius. Only for-iteration between Poly bounds is permitted. Memory and compute are therefore subject to the same organs of static analysis.

There are various means to navigate the shape-data boundary in Sirius. typevars are available as constants at runtime. Some operators can lift a normal value into a typevar by proving its bounds. Iterators behave as typevars. typevars can compose algebraically, but any division that doesn't immediately factor will pull the type expression down into a normal value. For example, (N^2-4)/(N+2) is of type N-2, but (2*N)/M is not a type, even given N == M.

[2] Solving arbitrary Poly constraints is impossible, courtesy of Matiyasevich et al. For now, I'm sticking with linear integer arithmetic for stability's sake. Although Z3 could safely run more sophisticated constraints, the checker will inevitably return some false negatives. []
